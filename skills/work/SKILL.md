# 개발 사이클 오케스트레이터

$ARGUMENTS 로 받은 작업을 아래 사이클로 수행한다.
메인 세션의 역할은 설계 대화·위임·보고 수신이다. 구현 세부 작업을 메인 세션에서 직접 하지 않는다.

**위임은 백그라운드가 기본**: 모든 에이전트 위임(3~5단계)은 run_in_background로 실행하고
즉시 턴을 종료해 메인 세션을 사용자에게 돌려준다. 사용자는 에이전트가 도는 동안
메인 세션에서 다른 대화·작업을 계속할 수 있어야 한다. 완료 알림을 받으면
결과를 보고하고 다음 단계 에이전트를 이어서 백그라운드로 위임한다.

## 1단계 — 설계 대화 (메인 세션, 사용자와)
- 요구사항을 분석하고 영향 범위(파일·모듈)를 파악한다. 코드 탐색이 필요하면 Explore 에이전트를 사용한다.
- 문제점·리스크·더 나은 대안이 보이면 구현 전에 반드시 지적한다. 무조건 동의 금지.
- 방안이 2개 이상이면 트레이드오프와 함께 제시하고 AskUserQuestion으로 승인을 받는다.

## 2단계 — 작업 명세서 작성
서브에이전트는 이 대화를 볼 수 없다. 자기완결적 명세를 작성한다. 필수 포함:
- 확정된 요구사항
- 승인된 설계·접근 방법
- 대상 프로젝트 경로, 작업 브랜치명 (feature/* 또는 fix/*)
- 제약: 건드리면 안 되는 파일, 따라야 할 기존 패턴의 예시 파일 경로
- 검증 명령: ./gradlew build, 테스트 명령 (프로젝트 CLAUDE.md 참조)
- 완료 기준: 무엇이 되면 끝인지

## 3단계 — 구현 위임
- implementer 에이전트에 명세서를 전달한다 (백그라운드 — 위 기본 규칙).
- 위임 직후 턴을 종료하고, 사용자와 다음 설계 대화를 계속한다.
- 여러 작업 병렬 위임: 서로 다른 프로젝트면 그대로 동시 실행한다.
  같은 저장소면 워킹 디렉토리가 충돌하므로 implementer를 worktree 격리
  (isolation: worktree)로 실행한다. 이때 규칙:
  - 브랜치와 worktree는 항상 쌍으로 신규 생성한다 (기존 브랜치 재사용 금지 —
    "already checked out" 충돌이 구조적으로 발생하지 않게 한다).
  - 메인 워킹트리(사용자 폴더)의 체크아웃 브랜치는 절대 바꾸지 않는다.
  - 검토·머지는 체크아웃 없이 한다: git diff main..feature/x, git merge feature/x
    는 메인 워킹트리에서 그대로 가능하다.
  - 머지 완료 후 git worktree remove로 정리한다 (커밋은 공유 .git에 보존됨).
- 순차 작업(한 번에 하나)은 worktree 없이 일반 브랜치 생성으로 작업한다 —
  worktree는 빌드 캐시·디스크 중복 비용이 있어 병렬일 때만 쓴다.
- implementer가 질문 목록을 들고 복귀하면 사용자와 해소한 뒤 재위임한다.

## 4단계 — 리뷰 위임
- implementer 보고 수신 후, code-reviewer 에이전트에 브랜치/diff 범위를 전달한다.
- critical·warning 발견 시 implementer에 수정을 재위임한다 (최대 2회 반복, 그래도 남으면 사용자 보고).

## 5단계 — 독립 검증
- verifier 에이전트에 요구사항 목록과 검증 명령을 전달해 최종 확인시킨다.
- verifier 불합격(요구사항 미충족·빌드 실패)은 재위임하지 않고 **즉시 사용자에게
  실패 내역 그대로 보고한다.** implementer는 자체 검증을 통과한 뒤 보고하므로,
  이 단계의 실패는 명세 해석 차이거나 자체 검증이 틀렸다는 이상 신호다 —
  자동 재시도로 가리지 않고 사람이 판단한다.

## 6단계 — 통합 보고 (메인 세션, 사용자에게)
보고 형식:
1. 변경 파일 목록과 핵심 변경 요약
2. 빌드·테스트 결과
3. 리뷰 발견 사항과 조치 내역
4. verifier 검증 결과
5. 남은 이슈·후속 권장

보호 브랜치로의 머지는 diff 요약을 보고하고 사용자 확인을 받은 후에만 진행한다.

## 7단계 — 작업로그 자동 기록 (사용자에게 묻지 않는다)
보고 완료 후 위키 작업로그 `<사용자 홈>\wiki\작업로그\YYYY-MM.md`에 기록한다:

```markdown
### YYYY-MM-DD — <작업 제목>
- 프로젝트: <경로 또는 이름> / 브랜치: <브랜치명>
- 내용: 핵심 변경 1~2줄
- 결과: 빌드·테스트·리뷰 요약 1줄
```

- 최신 항목이 위로 가게 추가한다. 해당 월 파일이 없으면 생성한다.
- wiki\TODO.md에 이 작업과 일치하는 할 일이 있으면 완료 처리한다.
- 위키 폴더가 없는 머신이면 조용히 건너뛴다.
